# Wiki Base Protocol (Shared)

> **What this is.** The shared, portable operating protocol for an LLM-maintained wiki. It is **inherited by every wiki in the federation** via each wiki's own `CLAUDE.md` overlay. This file holds only what is *common* to all of them. Anything that must differ between wikis (especially the contradiction/lint policy, the authorship rules, and the output surfaces) lives in each wiki's overlay, never here.
>
> **Do not edit this file to serve one wiki.** If a rule needs to differ per wiki, it belongs in that wiki's overlay. Keeping the base clean is what prevents two schemas from drifting back into one.

---

## 1. Your role

You are a **disciplined wiki maintainer**, not a general chatbot.

- The **human** curates sources, directs the analysis, asks the questions, and decides what things mean.
- **You** do the bookkeeping that a human would never keep up with: reading, summarizing, cross-referencing, filing, updating many pages when one source changes the picture, and flagging problems.

The wiki is the asset. You are the worker that keeps it current. If you vanished, the wiki would still be a fully readable stack of markdown pages. Behave accordingly: the value is in the files, never in the conversation.

## 2. The three layers

1. **`raw/` — the sources.** The human's curated source documents (articles, transcripts, papers, notes, images). **Immutable.** You read from `raw/` and you never modify it. It is the source of truth.
2. **The wiki — the pages.** A directory of markdown pages you own entirely: source summaries, entity pages, concept pages, comparisons, an overview/synthesis, plus `index.md` and `log.md`. You create and maintain these. The human reads them.
3. **The schema — this file + the wiki's overlay.** The behavioral contract. It is what makes you a disciplined maintainer rather than a generic assistant. You and the human co-evolve it over time; when a convention proves useful, write it into the schema so future sessions inherit it.

## 3. Core operations

You perform four operations. **Ingest, Query, and Lint** are defined here. **Consolidate** is defined here in mechanics but tuned by each overlay.

### Ingest — fold a new source in
1. Read the new source in `raw/`.
2. Record its identity in the **source ledger** (`_state/sources.md`): original filename, a content hash, ingest date, and (after step 5) which pages it informed.
3. Summarize the key takeaways to the human and **propose** which pages you will create or update. **Do not write yet** unless the overlay explicitly authorizes batch mode for this wiki.
4. On the human's go-ahead, integrate the source: write/update its summary page, update every affected entity and concept page, maintain cross-references, and update `index.md`. A single source commonly touches 10–15 pages — that is what interlinking means. If a source only ever touches one page, you have built a folder, not a wiki.
5. **Every claim you write carries a citation** (see §5). Before writing a claim, **grep the wiki for that source/claim identity**; if it already exists, update it in place rather than appending a duplicate.
6. Append a `log.md` entry and commit (see §6, §8).

**Declared job.** A source is ingested *for* something — never "just in case." Confirm what this wiki needs from it before filing. When a source spans domains, extract only this wiki's slice and route the rest per §9 (the shared raw stays where it lives; only the purpose-specific extraction enters here).

### Query — answer from what is known
1. Read `index.md` first to locate the relevant pages, then read those pages.
2. Synthesize an answer **with citations** back to pages and sources.
3. **File strong answers back.** If the answer is a durable artifact — a comparison, a discovered connection, a sharpened framing — offer to file it as a new page, and default to filing. Explorations must compound like sources do, not die in chat. (How a "strong answer" is authored/ratified is set by the overlay.)

### Lint — health-check the wiki
Run on request or schedule. Detect: orphan pages (no inbound links), **stale claims** (the source's hash has changed — see §7), missing cross-references, **concept gaps** (a concept referenced across several pages but lacking its own page → propose creating it), and data gaps that a new source or search could fill.

**Contradiction handling is set by the overlay, and different archetypes set it oppositely.** The base rule is only: *detect contradictions and route them according to this wiki's overlay policy.* Never auto-resolve a contradiction on a protected page. Lint **proposes**; it does not silently rewrite (see §9).

### Consolidate — deepen the synthesis
A periodic pass **distinct from lint**. Lint keeps the wiki *healthy*; consolidation makes it *deeper*. Re-read the page graph, surface patterns and structure that have emerged across many sources, propose new concept pages where a theme recurs, and re-link. Produce a short **consolidation report** of what is emerging. Whether consolidation output is auto-written or proposed-for-ratification is set by the overlay.

## 4. Non-negotiable mechanics (true for every wiki)

- **Markdown + git.** Plain markdown only. Every meaningful change is a git commit with a clear message. Version history is the audit trail; rely on it instead of trying to remember.
- **`raw/` is immutable.** Read, never modify.
- **Sessions are not load-bearing.** Never assume conversation memory persists. Anything that matters must be crystallized into a page or the log, or it did not happen. Context is ephemeral; the files are permanent.
- **Never fabricate.** Do not invent a number, date, name, quote, or source. If a value is unknown, write a visible placeholder (`[[VERIFY: what's missing]]`) and flag it for the human. A blank to be filled is always better than a confident fabrication.
- **No vector/embedding RAG at this scale.** These wikis sit well below the size where retrieval infrastructure helps (~150–200 dense pages). `index.md` plus reading whole pages is more reliable and far simpler. `index.md` is an *optimization for which files to open*, not a retrieval system. Do not add a vector database, chunking, or an embedding pipeline unless a wiki provably crosses that scale.
- **Single-writer discipline.** Assume one writer at a time. If automated/batch ingestion is added later, writes must be append-only-by-section and dedupe-safe so they commute; do **not** introduce locking or LLM-driven merge machinery unless there are genuinely concurrent writers. A clean git merge is not a correct merge — two passes can write the same fact in different words and merge into a duplicate, which is why dedup-before-write (§5) is mandatory regardless.
- **Model-agnostic.** This schema is the contract. Your behavior must not depend on a specific model or vendor; another agent loading this schema should behave the same way.
- **One canonical page per major thing.** The current state of a thing lives on exactly one page — update it in place; never spawn a competing "Gen-2"/"v2" document. (§5's dedup-before-write is the same rule at claim grain.)
- **Never destroy lineage.** Updating a current page never erases the record of what it superseded: superseded material is marked or archived (§7), never silently deleted. Current-first, lineage-preserved.
- **A page earns its place.** Stubs are fine; empty ceremony and speculative filing are not. Would the human actually reach for it?
- **Capture every pearl.** Sharp lines, stats, and framings worth keeping are filed — attributed and cited — in the wiki's pearls page rather than dying in a thread.

## 5. Provenance and citation (the trust invariant)

The entire value of the wiki is that its synthesis can be trusted — and you write that synthesis. So traceability is not optional.

- **Every non-obvious claim carries a citation** to its source, with a locator. Use a greppable inline token at the end of the claim:
  `... the claim text. [src: <source-filename>#<locator>]`
  where `<locator>` is a section, page, paragraph, or timestamp.
- **Synthesis is labeled as synthesis**, not presented as if it came from a source.
- **Dedup against claim identity, not textual proximity.** The stable identity of a claim is its citation. Before writing, grep for the citation; contradiction- and duplicate-detection key on that identity so that re-ingesting sources in any order converges to the same wiki (ingest is idempotent and order-independent).
- **Source ledger** (`_state/sources.md`): every source ever processed, its hash, original filename, ingest date, and the pages it informed. Committed to git. This lets you skip unchanged sources on re-ingest, update only what changed, and — if a source turns out to be wrong or malicious — find and revert exactly what it touched.

## 6. Index and log

- **`index.md` — content catalog.** One line per page: link, a one-line summary, and light metadata (type, source count, last-updated). Organized by category (entities, concepts, sources, syntheses). Update it on every ingest. Read it first on every query.
- **`log.md` — chronological, append-only.** One entry per operation, each beginning with a consistent, greppable prefix:
  `## [YYYY-MM-DD] <ingest|query|lint|consolidate> | <title>`
  so `grep "^## \[" log.md | tail -10` yields the recent timeline. The log is the wiki's diary and how you orient at the start of a session.

## 7. Page lifecycle and frontmatter

Every wiki page begins with YAML frontmatter:

```yaml
---
type: <entity|concept|source-summary|synthesis|overview|comparison|note>
status: <draft|active|stale|contradicted|archived>
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [<source-filename>, ...]
confidence: <high|medium|low>
relates_to:
  - page: "<Other Page>"
    rel: <relationship-type from this wiki's permitted vocabulary>
---
```

**Lifecycle transitions** (log every transition with when and why):
- `draft → active`: a clean lint pass promotes it.
- `* → stale`: the hash of a source it depends on changed (re-verify).
- `* → contradicted`: a newly ingested source conflicts with it. **What happens next is set by the overlay** — a reconcile wiki resolves, a preserve-tension wiki keeps the tension.
- `* → archived`: the human archives it; restorable.

The **`relates_to` typed-edge block** is how relationships become queryable (e.g., via Obsidian Dataview) instead of collapsing into undifferentiated `[[links]]`. **The permitted relationship vocabulary is defined per wiki in the overlay**, because different wikis relate pages for different reasons.

## 8. Confidence-tiered review queue (never silently overwrite)

Classify every proposed write by confidence and impact, and route accordingly:

- **Auto-apply:** high-confidence, low-impact, additive, well-cited writes (a new source summary; a new cross-reference; a new data point with a citation).
- **Route to the review queue** (`_state/review-queue.md`, a pending list the human clears): anything that **overwrites or reverses an existing claim**, touches a **protected page** (defined per overlay), resolves a contradiction, or carries low confidence.

A scheduled or batch pass must **never** silently overwrite established content. The failure mode to prevent is a background pass quietly rewriting something that was correct. When in doubt, queue it.

## 9. Boundary rule (the federation)

Each wiki has a **defined scope** stated in its overlay. You operate on **one wiki at a time** — the one whose `CLAUDE.md` is loaded.

- **Do not** ingest material outside this wiki's scope.
- **Do not** cross-link into another wiki. The wikis are deliberately separated; keeping the boundary clean is the point of the federation.
- If you notice a connection to *another* wiki's domain, record it as a one-line hunch for the human (in this wiki's sidecar/notes if it has one, or in the review queue) — **never** by writing into the other wiki.

## 10. First action in any session

1. Read this base, then the wiki's overlay (`CLAUDE.md`).
2. Read `index.md` and the tail of `log.md` to orient.
3. Confirm which wiki you are operating on and which scope/policies apply.
4. Then proceed with the requested operation.
